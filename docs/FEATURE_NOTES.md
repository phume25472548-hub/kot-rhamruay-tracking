# มาตรฐานคู่มือฟีเจอร์

คู่มือฟีเจอร์อยู่ที่ `docs/features/` เขียนให้ AI หรือนักพัฒนาที่ไม่เคยเห็นฟีเจอร์นั้น เริ่มงานได้ถูกจุดโดยไม่ต้องไล่อ่านทั้งโปรเจ็ค และรู้ว่าทำเสร็จแล้วต้องได้ผลแบบไหน

ตัวอย่างจริง: `docs/features/tracking-parcel.md`

## เวลาจะแตะฟีเจอร์ที่มีอยู่

1. หาฟีเจอร์ใน `docs/features/README.md` แล้วอ่านคู่มือก่อนเปิดโค้ด
2. ดู `verified_commit` ถ้าเก่ากว่าโค้ด ให้รันคำสั่งนี้เพื่อดูว่ามีอะไรเปลี่ยน แล้วเชื่อโค้ดก่อนเสมอ

   ```bash
   git log --oneline <verified_commit>..HEAD -- <ไฟล์ในหัวข้อ "จะแก้อะไร ไปที่ไหน">
   ```

3. ห้ามทำให้ "กฎที่ห้ามพัง" เสียโดยไม่ได้รับอนุมัติจากเจ้าของระบบ
4. ถ้าเจอว่าคู่มือไม่ตรงกับโค้ด ให้แก้คู่มือในงานเดียวกัน ถ้าไม่แน่ใจว่าฝั่งไหนถูก ให้บันทึกใน "คำถามที่ยังเปิด" แล้วถามเจ้าของระบบ

## เขียนหรือแก้เมื่อไร

| งาน | ต้องทำ |
|---|---|
| เพิ่มฟีเจอร์ใหม่ | สร้างคู่มือ และเพิ่มในสารบัญ |
| เปลี่ยนพฤติกรรม กฎ หรือผลลัพธ์ | แก้คู่มือเดิม |
| แก้บั๊กที่ทำให้ความเข้าใจเดิมเปลี่ยน | แก้คู่มือเดิม |
| ย้ายหรือเปลี่ยนชื่อไฟล์หรือฟังก์ชันที่คู่มืออ้างถึง | แก้หัวข้อ "จะแก้อะไร ไปที่ไหน" |
| แก้บั๊กทั่วไป, refactor ที่พฤติกรรมเท่าเดิม, ปรับหน้าตา | ไม่ต้องแก้ |

ฟีเจอร์ 1 ชิ้นคือความสามารถที่ผู้ใช้มองเห็น เช่น "ติดตามพัสดุ" ไม่ใช่ไฟล์หรือ endpoint หนึ่งตัว แก้คู่มือใน commit เดียวกับโค้ด

ชื่อไฟล์: `docs/features/<area>-<ชื่อภาษาอังกฤษ>.md` เช่น `tracking-parcel.md`

## แม่แบบ

ทุกหัวข้อต้องมีและเรียงตามนี้ เพื่อให้ AI ข้ามไปส่วนที่ต้องการได้ทันที ถ้าไม่มีเนื้อหาให้เขียนว่า "ไม่มี"

````markdown
---
id: <area>-<ชื่อ>
status: ใช้งานได้ | ทำบางส่วน | ยังไม่เปิดใช้
routes: [<หน้าจอและ API>]
data: [<ที่เก็บข้อมูล เช่น ตัวแปรในหน่วยความจำ ไฟล์ ฐานข้อมูล>]
external: [<บริการภายนอก พร้อมสถานะ verified หรือ not verified with real service>]
verified_commit: <commit ล่าสุดที่เทียบคู่มือกับโค้ดแล้ว>
---

# <ชื่อฟีเจอร์ภาษาไทย>

## ทำอะไร
1-3 ประโยค: ทำอะไร ใครใช้ ใช้ตอนไหน และแก้ปัญหาอะไร

## ทำงานยังไง
ขั้นตอนจากการกระทำของผู้ใช้จนถึงผลที่แสดง แยกตามเส้นทางหลัก

## ผลที่คาดหวัง
| เมื่อ | ต้องได้ | ตรวจด้วย |
|---|---|---|
| เงื่อนไขที่ชัดเจน | ผลลัพธ์ที่ตรวจได้ | ชื่อเทสต์ หรือ "ไม่มีเทสต์" |

## กฎที่ห้ามพัง
เงื่อนไขที่ต้องจริงเสมอ และเหตุผลสั้นๆ ระบุว่าเป็นกฎของเจ้าของระบบหรือกฎทางเทคนิค

## ไม่ทำและข้อจำกัด
สิ่งที่ตั้งใจไม่ทำ และพฤติกรรมของโค้ดปัจจุบันที่ต้องระวัง

## จะแก้อะไร ไปที่ไหน
| อยากแก้ | เริ่มที่ |
|---|---|
| งานที่น่าจะเจอ | `path/file.js` → `functionName` |

## ตรวจงาน
คำสั่งที่รันได้จริง และขั้นตอนลองบนหน้าจอถ้ามี

## คำถามที่ยังเปิด
เรื่องที่รอเจ้าของระบบตัดสินใจ
````

## วิธีเขียน

- **ภาษา:** เนื้อหาเป็นภาษาไทย ส่วนชื่อโค้ดและ path ใช้ภาษาอังกฤษตามจริง
- **อ้างโค้ดด้วยชื่อ:** ใช้ path กับชื่อฟังก์ชันหรือ route ห้ามใช้เลขบรรทัด เพราะเลขเปลี่ยนเร็ว
- **เขียนสิ่งที่มีจริง:** แยกสิ่งที่โค้ดทำอยู่ออกจากสิ่งที่อยากให้เป็น ของที่ยังไม่ทำให้ใส่ใน "ไม่ทำและข้อจำกัด"
- **ทำให้ตรวจได้:** ใช้ผลลัพธ์ที่วัดได้ เช่น "ค้นเลข MOCK1 ได้ 5 รายการ ล่าสุดคือถึงโกดังไทย" ไม่ใช้คำอย่าง "แสดงผลถูกต้อง"
- **บอกความครอบคลุมตรงๆ:** ถ้าไม่มีเทสต์ให้เขียน "ไม่มีเทสต์" ห้ามอ้างเทสต์ที่ไม่ได้ตรวจเรื่องนั้นจริง
- **เขียนเฉพาะกฎของฟีเจอร์:** กฎกลางอยู่ใน `CLAUDE.md` ไม่ต้องคัดลอกมา
- **เรื่องเงินและค่าขนส่ง:** ห้ามเดา ถ้าไม่แน่ใจให้ใส่ใน "คำถามที่ยังเปิด"
- **ความยาว:** ไม่เกินราว 100 บรรทัด ถ้ายาวกว่านั้นอาจเป็นหลายฟีเจอร์ ให้แยกไฟล์

## เช็กก่อน commit

- [ ] มีครบทุกหัวข้อตามลำดับในแม่แบบ
- [ ] path และชื่อฟังก์ชันใน "จะแก้อะไร ไปที่ไหน" มีอยู่จริง
- [ ] ชื่อเทสต์ใน "ผลที่คาดหวัง" มีอยู่จริงและตรวจเรื่องนั้นจริง
- [ ] `verified_commit` ตรงกับ commit ล่าสุดที่เทียบคู่มือกับโค้ดแล้ว
- [ ] สถานะในสารบัญ `docs/features/README.md` ตรงกับคู่มือ
